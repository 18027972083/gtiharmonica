# 项目成果

> 更新：2026-09-19 · 对应产物 `dist\DeltaHarp\DeltaHarp.exe`（v0.2.0）

## 这是什么

**DeltaHarp**（原名 GTI Harmonica）—— 三角洲行动游戏内口琴的自动演奏工具。把 MIDI 或
下载来的歌曲变成游戏里能自动弹出来的按键序列，在游戏的口琴界面里自动
演奏；内置一个可编辑的乐谱编辑器，用来修正转录结果。

它是对原版 `GTIartist v1.1` 的**重写**，不是破解：原程序用 VMProtect
加壳做了激活校验，本项目只从它的行为里逆向出指法表与编排规则，然后
用自己的代码重新实现。运行时不依赖也不需要原程序。

## 本次交付的三块

### 1. 曲库不再丢失

**问题**：曲库原先放在 exe 旁边的 `songs\`，而那个位置正好在构建产物
`dist\` 内部。PyInstaller 每次重建会先整个删掉该目录；旧代码只把文件读进
内存、构建后再写回，一旦恢复环节出岔子就是**静默丢失**——上一次构建日志
明明写着「已恢复用户曲目」，文件却不在，用户自己转的谱就这样没了。

**改法**（两条独立防线）：

| 防线 | 位置 | 做法 |
|---|---|---|
| 曲库搬出构建产物 | `gtiharmonica/app.py` | 打包后默认 `%APPDATA%\GTIHarmonica\songs`；旧曲库首次启动自动合并（只补不覆盖、不删原件、幂等）。放 `portable.txt` 可保持便携 |
| 构建前后比对清单 | `build.py` | `library_manifest()` 快照 + `verify_library()` 逐文件校验，**缺一首就让构建报错退出**；用户曲目另落盘备份到 `build/songs-keep/`（不在 `dist/` 里） |

开发环境仍用项目根目录的 `songs\`，方便直接改曲谱。

### 2. 可编辑乐谱编辑器

转录是统计估计，总有切错、认错音的地方。与其反复调参数碰运气，不如直接
把谱子改对。

**新增两个模块**：

- `gtiharmonica/edit.py`（695 行）—— 编辑文档层：编辑命令、撤销重做、
  节拍与音阶吸附、碎片合并、存回 JSON
- `gtiharmonica/gui/editor.py` —— 编辑器界面：小节线/拍号渲染、选中与
  拖拽交互、工具行、信息行

**功能**：小节线与拍号渲染（顶部带小节号）、单击/Shift 加选、拖主体改音高
与位置、拖两端改时值（拖左端时终点钉死）、空白框选、双击插入、双击切开、
Delete 删除、方向键微调、`M` 合并、Ctrl+Z/Ctrl+Shift+Z 撤销重做、Ctrl+A
全选、滚轮滚动、Ctrl+滚轮缩放、中键平移；工具行有量化、调内吸附、清理
重叠；拍号/BPM/调号/调式可改且改完小节线立刻重排。

**「合并长音」是核心**——转录把长音切成一串碎片时的兜底手段。框选碎片点
一下即可；**什么都不选直接点则合并整首**（碎片往往散布全曲，手工框选不
现实）。合并按「时间相邻且音高相同」分组，不会把真正分开的音错并到一起。

**三个必须绕开的坑**（都写了专门的测试钉死）：

1. **编辑结果不能再走 `arrange()`**。那个函数会做移调与八度折叠，对已经
   定好的音高再折一次就是错音。新增 `arrange.arrange_from_notes()`，只重算
   指法、时间轴与换气。测试故意把 `transpose` 设成 7，断言音高纹丝不动。
2. **撤销会替换整个音符列表**，基于 `id()` 的选区会失效（用户会遇到
   「选中、撤销，选区空了」）。所以给每个音符挂了稳定 `uid`，`copy()` 会连它
   一起复制，选区就能跨撤销/重做/排序存活。
3. **按键行原本只在预览页**，编辑时看不到「这个音对应哪个键」。已移到两个
   视图之外共享，演奏时照样高亮。

### 3. 补齐测试缺口

老测试**全部用 C5**，而 C5 的相邻半音间距（31 Hz）刚好大于 1024 窗的频点
宽度（21.5 Hz）——它恰好绕开了低音区；而且只数音符个数、从不断言音高。
这就是上一版音高整体坏掉（音符 545→659、中位音高 C4→D4）时测试却全绿的
原因。

补上之后（转录验收 58 → 77 项），立刻测出一个**真实缺陷**：

```
孤立低音短音：36→55(+19)  40→59(+19)  43→62(+19)  45→64(+19)
              48→60(+12)  50→62(+12)  52→64(+12)
                G3(55) 往上：全部精确命中
```

G#3 以下孤立短音被系统性抬高；45 往下被抬到 **3 次谐波**（+19 = 12+7，
C2 的第 3 谐波正好是 G3）。原因是旋律先验（对数频率高斯，中心 380 Hz，
恰好是音域中点）压过了证据。**重要缓解**：连续低音音阶偏差为 0，说明有形
上下文时低音区是准的。

**这条没有掩盖，也没有顺手修**——改先验会影响所有已经正常的转录结果，
属于下一步的事。测试里如实记录了边界与幅度，防止它悄悄恶化。

另外补了一条**不跑转录、只检查物理约束**的测试：主分析窗 2048 的频点宽度
（10.8 Hz）小于相邻半音 C4→C#4 的 15.6 Hz，而 1024 窗的 21.5 Hz 大于它 ——
这正是上一版翻车的根因。只要有人再把分析窗缩短，这条断言就会失败。

## 已知限制（诚实清单）

完整的当前问题清单见 **[已知问题.md](已知问题.md)**（含复现方式、实测数字与
处理建议）。下面是摘要。

**物理层面的，不是缺陷**：

- 两个同频纯正弦首尾相接，波形完全连续 —— 它**本来就是一个音**，任何算法
  都分不开。真实音频因为有音色变化才有依据。
- 低音区 C3→C#3 只差 7.8 Hz，比主分析窗的频点宽度（10.8 Hz）还小，
  落在同一个 bin 里。要求分开是不讲道理。
- 3/4 与 4/4 在 1.5 / 2.0 这种 3:4 关系下本质难分。编辑器里可以手动选拍号。

**当前缺口**：

- **低音区孤立短音被抬高**（见上文），连续旋律不受影响。
- ~~**长音碎片识别的算法修复仍未完成**~~ **已解决（2026-09-18 第二轮）**：
  重起音判据改为**按音高自适应窗长的时域复解调**（`REATTACK_CYCLES=26`，
  低音长窗保频率分辨率、高音短窗保时间分辨率），`reattack_min` 默认 0.28
  开启。真实曲谱长音保留：青花瓷 1→39、父亲 9→51、call of silence 35→52。
  当年「判据一开音高就被抬高」经插桩证明是碎音丢弃造成的计数伪影（帧级
  音高轨迹在判据开关下完全相同），勘误详见 `已知问题.md` P1。
- **编辑器里点击不能定位播放头**（点击被用作选择），定位请用时间轴滑块。
- **游戏内实际演奏未验证** —— 需要游戏环境，听感需自行实测校准。
